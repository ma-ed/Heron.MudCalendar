## Project Overview

**Heron.MudCalendar** is a Blazor component library providing a calendar widget for [MudBlazor](https://mudblazor.com/). It targets **net8.0**, **net9.0**, and **net10.0** and is published as a NuGet package.

## Solution Files

- `Heron.MudCalendar.sln` — Core library + tests (use this for day-to-day development)
- `Heron.MudCalendarWithDocs.sln` — Includes the documentation site (requires a companion MudBlazor fork checked out alongside this repo)

## Common Commands

```bash
# Restore dependencies
dotnet restore Heron.MudCalendar.sln

# Build the library (single-threaded required — see below)
dotnet build Heron.MudCalendar/Heron.MudCalendar.csproj -c Debug -m:1

# Run all unit tests
dotnet test Heron.MudCalendar.UnitTests/Heron.MudCalendar.UnitTests.csproj -c Release

# Run a single test (by name filter)
dotnet test Heron.MudCalendar.UnitTests/Heron.MudCalendar.UnitTests.csproj -c Release --filter "FullyQualifiedName~TestName"

# Pack NuGet package
dotnet pack Heron.MudCalendar/Heron.MudCalendar.csproj -c Release -m:1 --output nupkgs /p:PackageVersion=X.Y.Z

# Compile SCSS / watch for changes (run from Heron.MudCalendar/ directory)
dotnet webcompiler ./Styles/Heron.MudCalendar.scss -c excubowebcompiler.json
dotnet watch webcompiler ./Styles/Heron.MudCalendar.scss -c excubowebcompiler.json
```

> **Important:** Always use `-m:1` for builds. `Directory.Build.props` enforces single-threaded builds globally to prevent file-lock conflicts when multi-targeting.

## Architecture

### Projects

| Project | Purpose |
|---|---|
| `Heron.MudCalendar/` | Main Razor component library — the published NuGet package |
| `Heron.MudCalendar.UnitTests/` | NUnit + bunit unit tests |
| `Heron.MudCalendar.UnitTests.Viewer/` | Blazor WASM app for manually viewing test components |
| `Heron.MudCalendar.UnitTests.Viewer.Server/` | Backend for the test viewer |
| `Heron.MudCalendar.Docs/` | Documentation site (Blazor WASM, deployed to GitHub Pages) |

### Main Library Layout (`Heron.MudCalendar/`)

- `Base/` — Abstract base classes (`CalendarViewBase`, `DayWeekViewBase`) shared by the view components
- `Components/` — Razor components (calendar cells, items, month/week/day views)
- `Enums/` — Shared enumerations
- `Extensions/` — Extension methods
- `Resources/` — `.resx` localization files for 20+ languages
- `Scripts/` — JavaScript source files; a pre-build target combines them into `Scripts/combined/Heron.MudCalendar.js`
- `Styles/` — SCSS source; compiled by Excubo WebCompiler to `wwwroot/Heron.MudCalendar.min.css`
- `wwwroot/` — Final minified CSS and JS outputs (checked in; regenerated by pre-build)

### Pre-Build Pipeline

The `.csproj` defines MSBuild targets that run before compilation:
1. **ToolRestore** — `dotnet tool restore` (restores Excubo.WebCompiler 4.3.0)
2. **CombineJS** — Concatenates `Scripts/*.js` into `Scripts/combined/Heron.MudCalendar.js`
3. **WebCompiler** — Compiles SCSS → CSS and minifies CSS + JS
4. **IncludeGeneratedStaticFiles** — Validates and includes minified assets in the build output

When editing styles (`Styles/`) or scripts (`Scripts/`), the pre-build step handles regeneration automatically on the next build. Use `dotnet watch webcompiler` for a live feedback loop.

### Testing Stack

- **bunit** — Blazor component rendering in tests
- **NUnit 4** + **FluentAssertions** — Test framework and assertions
- Tests live under `Heron.MudCalendar.UnitTests/`; mirror the library's folder structure

### Docs Site Build Requirements

The docs site (`Heron.MudCalendar.Docs/`) references a forked MudBlazor checkout. To build it locally you need:
```
ParentDir/
├── MudBlazor/          ← branch: mudcalendar
└── Heron.MudCalendar/
```
Build order: MudCalendar (Debug) → MudCalendar (Release) → MudBlazor.Docs (Release) → MudCalendar.Docs (Release).
